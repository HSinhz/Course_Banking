1Single server setup

Start simple: web app, database and cache all live on one machine.

Every system starts here. It is cheap, fast to build and easy to reason about. The interesting part is the request flow: what happens between typing a URL and seeing a page.

The 4 steps

  1. DNS lookup – users type a domain name; DNS (usually a paid third-party service, not your server) maps it to an IP.
  2. IP returned – the browser/app gets e.g. 15.125.23.214 and caches it for a while.
  3. HTTP request – sent directly to that IP / web server.
  4. Response – HTML for browsers, JSON for mobile apps.

Two traffic sources

Web application

Server-side language (Java, Python…) for business logic and storage; client-side HTML + JavaScript for presentation.

Mobile application

Talks to the server over HTTP. JSON is the usual format because it is light and easy to parse. Example: GET /users/12 returns the user object with id, name, address, phone numbers.
Limit: one machine = one point of failure, and web, DB and cache all fight for the same CPU/RAM.

2Separate the database (web tier vs data tier)

First scaling step: move the database to its own server.

When users grow, put the web/mobile traffic (web tier) and the database (data tier) on different servers. Now each can be scaled on its own: a CPU-heavy web tier needs more compute; a data-heavy DB needs more disk and RAM.

Why it matters: independent scaling, independent failure, and you can apply different security rules (DB not exposed to the internet).

3Which database: SQL or NoSQL?

Default to relational; pick NoSQL when you have a specific reason.

Choose NoSQL if…

  • You need super-low latency.
  • Data is unstructured or has no relations.
  • You only serialize/deserialize data (JSON, XML, YAML).
  • You must store a massive amount of data.
Real systems often use both: SQL for core business data (orders, payments) and NoSQL for sessions, logs, feeds.

4Vertical vs horizontal scaling

Scale up (bigger machine) vs scale out (more machines).

Vertical (scale up)Horizontal (scale out)
HowAdd CPU, RAM, disk to one serverAdd more servers to a pool
ProsSimple; great when traffic is lowNo hard limit; failover and redundancy
ConsHard hardware limit; no failover (server down = site down); expensiveMore complexity (needs load balancer, stateless design)
Rule of thumb: scale up first while it is cheap and easy; design for scale out before you hit the ceiling.

5Load balancer

One public entry point that spreads traffic across many web servers.

Users connect to the load balancer's public IP. Web servers are no longer reachable directly; the balancer talks to them over private IPs (reachable only inside your network), which improves security.

What it solves

  • Failover: if Server 1 dies, all traffic goes to Server 2 and a new healthy server is added.
  • Scalability: traffic spikes? Add servers to the pool; the balancer starts using them automatically.
  • Security: only the balancer is public; servers use private IPs.

Good to know

  • Algorithms: round robin, least connections, IP hash, weighted.
  • It does health checks to detect dead servers.
  • The load balancer itself can become a SPOF, so in production they are deployed in redundant pairs (or managed, e.g. AWS ELB).

6Database replication

Master handles writes; slaves hold copies and handle reads.

Failure handling

Better performance

Most apps read far more than they write, so many slaves serve reads in parallel.

Reliability

Data is copied to several locations; a disaster at one site does not lose data.

High availability

If one DB is offline, another serves the data.
Caveat: replication is usually asynchronous, so a slave can be slightly behind. Promoting a slave to master may need recovery scripts for missing data. Multi-master and circular replication exist but are more complex.

7Cache

Keep hot data in memory so most requests never reach the database.

The cache tier is much faster than the database, reduces DB load, and can be scaled independently. APIs are simple, e.g. Memcached: cache.set('myKey','hi there',3600) and cache.get('myKey').

Considerations

When to use

Data that is read often, changed rarely. Cache is volatile; never the only copy of important data.

Expiration (TTL)

Too short → constant DB reloads. Too long → stale data. Always set one.

Consistency

DB and cache updates aren't one transaction, so they can drift apart; harder across regions.

Avoid SPOF

Use several cache servers across data centers and over-provision memory as a buffer.

Eviction

When full, old items are removed. LRU (least recently used) is most common; also LFU, FIFO.

8Content Delivery Network (CDN)

Serve static files from a server geographically close to the user.

Considerations

  • Cost: you pay per data transfer; don't put rarely used assets on the CDN.
  • Cache expiry (TTL): not too long (stale), not too short (constant origin reloads).
  • Fallback: if the CDN is down, clients should fall back to the origin.
  • Invalidation: use the vendor API, or versioned URLs like image.png?v=2.
After CDN + cache: static assets no longer hit web servers, and database load drops thanks to caching.

9Stateless web tier

Keep session state out of the web servers so any server can handle any request.

Stateful

Server remembers the client between requests. Requests must be pinned to one server (sticky sessions). Adding/removing servers and handling failures is hard.

Stateless

Servers keep no client state; they fetch it from a shared store (relational DB, Redis/Memcached, NoSQL). Simpler, more robust, easy to auto-scale.

With state removed, auto-scaling becomes straightforward: add or remove web servers automatically based on CPU or request load.

10Multiple data centers

Serve users from the closest region; survive a full-region outage.

geoDNS resolves the same domain to different IPs depending on where the user is. In an outage, traffic is sent 100% to the healthy data center.

Technical challenges

ChallengeApproach
Traffic redirectiongeoDNS / geo-routing to the nearest healthy DC.
Data synchronizationReplicate data across DCs (e.g. Netflix's asynchronous multi-DC replication), so failover traffic finds its data.
Test & deploymentTest from each location; use automated deployment to keep every DC identical.

11Message queue

Decouple components with asynchronous communication.

Example: photo processing

Benefits: loose coupling, failure resilience, smoother traffic spikes, independent scaling. Typical tools: RabbitMQ, Kafka, SQS.

12Logging, metrics, automation

Optional for a small site; essential for a big business.

Logging

Watch error logs per server, or aggregate to a central service for easy search.

Metrics

Host level: CPU, memory, disk I/O.
Aggregated: DB tier, cache tier performance.
Business: daily active users, retention, revenue.

Automation

Continuous integration verifies every check-in; automate build, test, deploy to raise productivity and consistency.

13Database scaling: sharding

Split a huge database into smaller shards across servers.

Vertical scaling of a DB (e.g. 24 TB RAM servers exist) helps a long way, but has hardware limits, SPOF risk and high cost. Horizontal scaling = sharding: every shard has the same schema but holds different rows.

The sharding (partition) key (here user_id) is the most important decision. It should spread data evenly and let you route each query to exactly one shard.

New challenges introduced

Resharding

A shard fills up or data is uneven → change the hash function and move data. With % N, changing N remaps almost everything. Consistent hashing moves only a small fraction (see below).

Celebrity / hotspot

Katy Perry, Justin Bieber and Lady Gaga on one shard will overload it. Give hot keys their own shard, possibly split further.

Joins & denormalization

Cross-shard JOINs are hard. Denormalize so a query needs a single table.

Consistent hashing (for resharding)

In the final design, some non-relational workloads (sessions, logs, feeds) are moved to a NoSQL store to take even more load off the sharded relational databases.

Summary: key takeaways

  • Keep the web tier stateless.
  • Build redundancy at every tier (LB, web, DB, cache, data center).
  • Cache as much data as you can.
  • Host static assets on a CDN.
  • Scale the data tier by sharding; move suitable data to NoSQL.
  • Split tiers into independent services and decouple with message queues.
  • Monitor the system and use automation tools.

Scaling is iterative: measure, find the bottleneck, add the simplest block that fixes it, repeat.
