How it holds on Postgres
THE KEY IS THE LAW

hai request song song, một key → Postgres để một thắng, cái kia lãnh 23505.

schema · the arbiterDDL
CREATE TABLE "IdempotencyRecords" (
  "Key" text PRIMARY KEY, -- = UNIQUE + NOT NULL = trọng tài chống trùng
  "Status" int, "ResponseBody" text, "CreatedAt" timestamptz
);

① INSERT-first Không dùng SELECT rồi INSERT (có khe hở race giữa 2 lệnh). Cứ INSERT thẳng và để ràng buộc khoá làm trọng tài.
② Row lock · B chờ A Khi A đã INSERT key nhưng chưa commit, B INSERT cùng key sẽ bị chặn (chờ) cho tới khi A commit/rollback — Postgres không cho hai bản ghi cùng khoá tồn tại.
③ 23505 · unique_violation A commit → B nhận duplicate key value violates unique constraint (SQLSTATE 23505). App bắt lỗi này và trả cache thay vì trừ tiền lần nữa.
④ Một transaction nguyên tử Claim key + trừ/cộng tiền + đóng dấu Completed trong cùng một transaction → key và tiền luôn đồng bộ: hoặc cả hai, hoặc không gì.
Another arbiter
BUSINESS KEY

không cần key kỹ thuật — chính dữ liệu nghiệp vụ làm khoá chống trùng.

ALTER TABLE "Orders"
  ADD CONSTRAINT prevent_dup_order
  UNIQUE (user_id, checkout_session_id); -- danh tính = tổ hợp cột nghiệp vụ, không phải UUID riêng

Client không cần gửi key Server tự suy danh tính từ dữ liệu lệnh (user + session). Client quên/sai key vẫn chặn được.
Chặn tuyệt đối & vĩnh viễn UNIQUE trên cột nghiệp vụ → cùng tổ hợp là không bao giờ tạo được bản ghi thứ hai.
Cần định nghĩa "thế nào là trùng" Phải chọn đúng tổ hợp cột. Sai → chặn oan lệnh lặp hợp lệ, hoặc bỏ sót.
Idempotency-Key vs Business key Một bên = UUID kỹ thuật client gửi; một bên = thuộc tính nghiệp vụ server tự có. Bổ sung nhau.

Not one wall — five
DEFENSE IN DEPTH

chọn một mối đe doạ → xem nó bị chặn ở lớp nào. Lớp càng sâu càng đáng tin.

L5 · recovery Lưới an toàn nền: Outbox worker (P14) chạy lại lệnh bị crash · Reconciliation (P16) đối soát giao dịch kẹt Pending.
Bấm một mối đe doạ để xem lớp nào chặn nó. Defense in depth = nhiều lớp độc lập; một lớp thủng vẫn còn lớp sau.
